# Altimeter: руководство для агента

Этот файл описывает назначение, устройство и правила сопровождения проекта. Перед анализом задачи или изменением кода изучите этот документ, обычный `README.md` и непосредственно затрагиваемые исходники. Код является источником истины, если документация и реализация расходятся.

## Назначение проекта

Altimeter — нативное Android-приложение с офлайн-ориентированным высотомером, компасом и записью профиля высоты для Android 8.0 и новее. Google Play Services не требуются.

Основные возможности:

- показ координат, названия места, состояния GNSS и числа видимых/используемых спутников;
- компас с магнитным севером до получения координат и истинным севером после расчёта магнитного склонения;
- расчёт высоты над средним уровнем моря по GNSS и, при наличии барометра, гибридно по GNSS и давлению;
- ручная калибровка высоты по известному значению или справочной высоте рельефа;
- показ высоты рельефа Copernicus DEM GLO-90;
- показ давления с датчика телефона или, если датчика нет, из погодных данных;
- текущая погода Open-Meteo и прогноз на ближайшие 24 часа / 7 дней;
- однократное предупреждение об отсутствии нужного оборудования и постоянные сведения в настройках;
- ручной запуск фоновой записи профиля высоты;
- локальная история записей, график, минимум, максимум, набор и сброс высоты;
- экспорт завершённых записей в GPX и CSV через системное меню «Поделиться»;
- интерфейс на 12 языках и системный выбор языка;
- сохраняемые точки возврата, форматы координат DD/DMS/UTM/MGRS и цель на компасе;
- высотные пороги со звуковым уведомлением во время записи;
- светлая / тёмная тема с системным или ручным выбором;
- независимый выбор единиц высоты/расстояния, давления, температуры и скорости ветра.

Приложение не содержит карт, аккаунтов, рекламы, аналитики, платных API и облачной синхронизации. Треки и кэши хранятся локально. Резервное копирование и перенос данных средствами Android явно отключены.

Приложение предназначено для бытового использования и походов, но не для авиации, геодезии, спасательных или иных критичных задач.

## Сборка и проверка

Нужны JDK 17+ и Android SDK 36. Скрипт `tools/gradle-android.sh` обнаруживает SDK через `ANDROID_HOME`, `ANDROID_SDK_ROOT`, локальный `local.properties` или стандартные каталоги.

Основная проверка:

```bash
make check
```

Отдельные команды:

```bash
make unit
make lint
make assemble
make emulator-check
make device-check
```

`make emulator-check` создаёт изолированный Gradle Managed Device `pixel2Api29`, запускает instrumentation-тесты и завершает эмулятор. `make device-check` требует уже запущенный эмулятор или подключённое Android-устройство. Debug APK создаётся в `app/build/outputs/apk/debug/app-debug.apk` и устанавливается командой:

```bash
adb install -r app/build/outputs/apk/debug/app-debug.apk
```

Release-сборка включает R8/minification и использует `app/proguard-rules.pro`. В репозитории нет конфигурации подписи release APK. GitHub Actions выполняет стандартную проверку и instrumentation-тесты на Android Emulator.

После изменения:

- чистой Kotlin-логики запускайте как минимум `testDebugUnitTest`;
- Android-ресурсов, Compose UI, manifest или разрешений — также `lintDebug` и `assembleDebug`;
- foreground service, разрешений и жизненного цикла — по возможности `connectedDebugAndroidTest` и ручную проверку на Android 8–12 и Android 13+;
- Room-сущностей — обновляйте версию БД, миграции и экспортированную схему в `app/schemas/`; не рассчитывайте на destructive migration, она не настроена;
- пользовательских строк — синхронно обновляйте `values/strings.xml` и `values-ru/strings.xml`.

## Архитектура

Архитектура лёгкая, без отдельного DI-фреймворка и без формально выделенных use case. Главные уровни:

```text
Android sensors / LocationManager / Open-Meteo
                    │
                    ▼
 LiveRepository ── AltitudeEngine ── SettingsRepository
       │                 │                    │
       └─────────────────┴────────────────────┘
                         │ LiveReading / UserSettings
                         ▼
                    MainViewModel
                         │ AppUiState
                         ▼
                 Jetpack Compose UI

TrackingService ── LiveRepository ── TrackRepository ── Room
                                             │
                                      TrackExporter
```

`AltimeterApplication` создаёт единственный `AppContainer`. Контейнер вручную собирает базу, репозитории и движок высоты, а также общий application scope (`SupervisorJob + Dispatchers.Default`). Эти объекты живут всё время процесса приложения.

`MainActivity` отвечает за Compose root, runtime-разрешения, смену языка и запуск системного share intent. `MainViewModel` объединяет потоки live-данных, настроек, статуса записи и списка сессий в `AppUiState`.

`LiveRepository` имеет reference-counted модель владельцев. Activity и foreground service вызывают `acquire()`/`release()` со своими идентификаторами; датчики и LocationManager работают, пока существует хотя бы один владелец. При изменении этой логики нельзя допустить, чтобы уход Activity в фон останавливал данные активного сервиса или чтобы несколько владельцев регистрировали слушатели повторно.

## Основные компоненты

### Точка входа и контейнер

- `AltimeterApplication.kt` — `Application` и ручной dependency container.
- `MainActivity.kt` — единственная Activity. Запрашивает precise/coarse location, а на Android 13+ отдельно уведомления перед началом записи. Разрешение background location не используется.
- Язык переключается через `AppCompatDelegate.setApplicationLocales`: системный или один из 12 поддерживаемых языков.
- Live-источники приобретаются на `ON_START` Activity и освобождаются на `ON_STOP`.

### Доменные модели

`model/Models.kt` содержит модели без Android UI-зависимостей:

- `LiveReading` — агрегат координат, места, высоты, рельефа, компаса, GNSS, давления и погоды;
- `AltitudeReading` — высота MSL, точность, источник, время и признак ручной поправки;
- `UserSettings` — единицы, формат координат, язык, активная точка, удержание экрана, калибровочная поправка и подтверждение предупреждения об оборудовании;
- `DeviceCapabilities` — наличие GNSS, барометра и источников компаса независимо от разрешений / включения GPS;
- `WeatherForecast` — часовой пояс места, почасовой и дневной прогноз;
- `TrackingState` — активность, id/время сессии и число точек;
- enum-ы источников, единиц, языка, состояния GNSS и типа погоды.

Внутренние расчёты и хранение выполняются в метрической системе: метры, hPa, °C, м/с. Перевод в пользовательские единицы выполняется на границе UI/уведомления.

### Live-данные, датчики и GNSS

`location/LiveRepository.kt` агрегирует данные устройства:

- местоположение запрашивается у GPS каждые 1 с без минимальной дистанции и у network provider каждые 5 с/10 м, если он доступен;
- только GPS-локация считается прямым свидетельством GNSS-фикса;
- координаты запускают обновление погоды/рельефа и reverse geocoding;
- название места обновляется после перемещения не менее чем на 100 м и зависит от системного `Geocoder`;
- основной источник компаса — `TYPE_ROTATION_VECTOR`, fallback — акселерометр плюс магнитометр;
- матрица компаса переназначается с учётом поворота дисплея;
- до получения координат UI честно показывает магнитный север; после расчёта склонения из `GeomagneticField` — истинный;
- итоговый азимут проходит круговой EMA-фильтр с обработкой перехода через 0°/360°;
- точность датчика и сила магнитного поля отражаются в UI и используются мастером калибровки;
- ненадёжная точность датчика отражается в UI как рекомендация откалибровать компас;
- давление датчика сглаживается EMA с коэффициентом 0,2;
- если барометра нет, давление берётся из актуального или закэшированного ответа Open-Meteo.

`location/GnssStateResolver.kt` изолирует особенности vendor GNSS:

- `GnssRuntimePolicy` централизует и тестирует выбор standard/VIVO runtime-пути; Sony и Samsung не должны получать отдельный GPS-listener, legacy extras, VIVO recovery-запросы или full tracking;
- Sony и Samsung используют проверенный legacy overload `requestLocationUpdates`, поскольку современный `LocationRequest` на Samsung Galaxy S24 с Android 16 запускает спутниковые callbacks, но не доводит GNSS до фикса;
- на Android 12+ VIVO запрашивает прямой GPS provider современным high-accuracy `LocationRequest` с максимальной частотой;
- свежая GPS-локация, валидное NMEA, `onFirstFix` или `usedInFix > 0` удерживает состояние `FIXED` 30 секунд;
- официальный callback `onFirstFix` служит подтверждением первого GNSS-фикса на всех устройствах;
- VIVO получает отдельный listener именно GPS-запроса, поэтому источник определяется по регистрации, а не по потенциально vendor-зависимой строке `Location.provider`;
- на VIVO X100 Ultra прямой GPS-запрос работает на максимальной частоте; параллельно приложение держит отдельный `getCurrentLocation(GPS_PROVIDER)` с ограниченным временем ожидания и повторяет его после ответа или тайм-аута, потому что некоторые сборки OriginOS не отдают результат непрерывному listener-у, но отвечают на one-shot запрос;
- дополнительный high-accuracy запрос к системному `fused` provider заставляет OriginOS задействовать системный навигационный путь; Google Play Services для этого не нужны;
- на VIVO X100 Ultra во время активной GNSS-сессии запрашивается full tracking через `GnssMeasurementRequest` с активным интервалом 0 и однократно запрашивается инъекция системного времени/PSDS/XTRA, чтобы OriginOS не удерживал чипсет в duty-cycling или без assistance data при холодном старте; все дополнительные listener-ы снимаются вместе с остальными GNSS-listener-ами;
- `fused`-локация считается подтверждением GNSS-фикса только если сама `Location` явно сообщает provider `gps`; высота, вертикальная точность и хорошая горизонтальная точность не являются доказательством GNSS, потому что OriginOS добавляет их и к network-локациям;
- валидные NMEA GGA/GNS/GSA/RMC служат дополнительным подтверждением фикса на всех устройствах; недостоверное или частичное число спутников остаётся `null`;
- спутники считаются уникально по паре `constellation + SVID`, поэтому несколько частот одного аппарата не раздувают числитель и знаменатель;
- число видимых спутников сглаживается максимумом за последние 10 секунд, чтобы частичные и чередующиеся пустые vendor-кадры не мигали в UI;
- положительное число `usedInFix` считается свежим 10 секунд; после этого при ещё свежем независимом подтверждении фикса число становится неизвестным, а не ложным нулём;
- пока подтверждение GPS-фикса остаётся свежим, пустой vendor-кадр не сбрасывает последние достоверные числа;
- после истечения свидетельства фикса состояние возвращается в `SEARCHING`;
- выключенный GPS и отсутствие разрешения представлены отдельными состояниями.

Не заменяйте эту логику прямой проверкой только `GnssStatus.usedInFix`: VIVO X100 Ultra и некоторые другие устройства могут публиковать корректные GPS-локации, но не выставлять этот флаг стабильно. Во время поиска без каких-либо свидетельств фикса `usedInFix = 0` отображается как честное `0/N`. Если фикс независимо подтверждён, но число используемых спутников нельзя достоверно получить ни из `GnssStatus`, ни из NMEA, модель хранит `null`, а UI сообщает о недоступности числа вместо ложного `0/N`.

`location/GnssDiagnosticLogger.kt` реализует выключенное по умолчанию диагностическое логирование. Оно кодирует JSON и пишет ограниченный двумя файлами JSONL-поток через единственную IO-coroutine, не сохраняет точные координаты и исходные NMEA-строки и создаёт согласованный snapshot перед системным `ACTION_SEND`. Включение логирования посреди активной сессии записывает `diagnostic_context`, но не перезапускает LocationManager. В лог входят Build-поля, выбранная compatibility-ветка и режим GPS-запроса, результаты регистрации, `onFirstFix`, очищенные NMEA-признаки, Location metadata, сырые и уникальные счётчики спутников. Raw-measurement callback регистрируется только как часть VIVO full-tracking workaround: даже пассивный `GnssMeasurementRequest` нельзя добавлять standard-устройствам, поскольку на Samsung Galaxy S24 с Android 16 при нём переставал появляться фикс. Файл передаётся только явным действием пользователя.

### Вычисление высоты

`altitude/AltitudeEngine.kt` выдаёт высоту над средним уровнем моря:

1. GNSS-высота WGS84 преобразуется в MSL через `AltitudeConverterCompat`.
2. Если MSL уже присутствует в `Location`, используется готовое значение.
3. Если геоидное преобразование не удалось из-за I/O, сырая WGS84-высота применяется как крайний fallback.
4. При наличии барометра хороший GNSS-фикс с вертикальной точностью не хуже 30 м создаёт/корректирует pressure anchor.
5. Между GNSS-фиксациями относительное изменение высоты считается по изменению давления.
6. Anchor корректируется к GNSS медленно, с коэффициентом 0,05, чтобы избежать резких скачков.
7. Результат проходит медианный фильтр окна 5 и EMA с коэффициентом 0,25.
8. В конце добавляется постоянная пользовательская калибровочная поправка из DataStore.

При барометре источник результата — `FUSED`; без него — `GNSS`; при ненулевой ручной поправке публичный источник становится `MANUAL`. Значение `BAROMETER` предусмотрено моделью, но текущим движком напрямую не публикуется.

Одновременно выполняется не более одного GNSS→MSL-преобразования (`AtomicBoolean`). Плохой первый фикс может заполнить пустой dashboard, но не калибрует барометр до появления приемлемой точности.

### Погода и высота рельефа

`weather/OpenMeteoRepository.kt` использует два endpoint-а без API-ключа:

- `https://api.open-meteo.com/v1/forecast` — текущая температура, ощущаемая температура, влажность, код погоды, ветер, давление у поверхности, дневной/ночной режим; почасовые и дневные температура, код погоды, вероятность осадков и ветер на 7 дней;
- `https://api.open-meteo.com/v1/elevation` — высота рельефа Copernicus DEM GLO-90.

Правила обновления:

- погода устаревает через 15 минут или после перемещения на 1 км;
- рельеф устаревает через 24 часа или после перемещения на 100 м;
- повторная попытка ограничена backoff 5 минут;
- одновременно выполняется не более одного refresh;
- connect/read timeout равны 10 секундам;
- успешные ответы, включая почасовой и дневной прогноз, сохраняются в Room;
- часы и даты прогноза разбираются в часовом поясе места из ответа API; UI скрывает прошедшие интервалы и помечает устаревший кэш;
- при ошибке последнее значение остаётся доступным с `stale = true`;
- запрос погоды и запрос рельефа выполняются последовательно в одном refresh job.

`OpenMeteoParser` преобразует WMO weather code в `WeatherKind`. Если меняется контракт Open-Meteo, обновляйте парсер, тесты и модели кэша согласованно.

### Настройки и калибровка

`data/SettingsRepository.kt` хранит Preferences DataStore `settings`:

- единицы расстояния/высоты;
- единицы давления;
- единицы температуры;
- единицы скорости ветра;
- язык;
- формат координат, активная точка возврата и режим удержания экрана;
- режим темы `theme_mode`: `SYSTEM` по умолчанию, `LIGHT` или `DARK`;
- калибровочную поправку в метрах;
- шаг записи высоты в метрах (по умолчанию 5 м);
- интервал выборки live-состояния foreground service (по умолчанию 1 с);
- максимально допустимый возраст координат записываемой точки (по умолчанию 10 с).
- явное включение GNSS-диагностики (по умолчанию выключено);
- подтверждение однократного предупреждения об оборудовании (`hardware_notice_acknowledged`). До загрузки DataStore оно равно `null`, чтобы предупреждение не мигало при запуске.

Есть совместимость со старым ключом `unit_system`; не удаляйте её без отдельного решения о миграции пользовательских данных. По умолчанию используются метры, мм рт. ст., °C, м/с и системный язык.

Калибровка не заменяет измерение: `MainViewModel` вычисляет новый offset как старый offset плюс разница между целевой и текущей отображаемой высотой. Поправка применяется ко всем последующим значениям, пока пользователь её не сбросит.

### Фоновая запись и история

`service/TrackingService.kt` — started foreground service типа `location`:

- запускается только явным действием пользователя;
- сразу показывает постоянное low-priority уведомление;
- имеет кнопку остановки в уведомлении;
- захватывает partial wake lock на время записи;
- становится отдельным владельцем `LiveRepository`;
- сэмплирует `LiveReading` с пользовательским интервалом, по умолчанию раз в секунду;
- обновляет уведомление не чаще чем раз в 10 секунд;
- возвращает `START_STICKY` и при перезапуске восстанавливает незавершённую сессию из Room.

`data/TrackRepository.kt` сериализует изменения через `Mutex`. Новая точка сохраняется только когда:

- есть рассчитанная высота;
- это первая точка либо высота отличается от последней сохранённой не менее чем на выбранный шаг, по умолчанию 5 метров.

Координаты прикрепляются к точке только если они не старше выбранного допустимого возраста, по умолчанию 10 секунд. Все три параметра применяются к активной записи сразу после изменения в настройках. На каждой сохранённой точке обновляются минимум, максимум, суммарный положительный набор, суммарный сброс и счётчик. Активную сессию нельзя удалить. Экспорт доступен только завершённым сессиям.

### Локальная база

Room-база `altimeter.db`, версия 3 (цепочка миграций 1 → 2 → 3 сохраняет треки и кэши), содержит семь таблиц:

- `track_sessions` — границы сессии и агрегированная статистика;
- `track_points` — время, координаты, MSL-высота, давление, точности и источник;
- `weather_cache` — единственная запись с id 1, включая JSON прогноза для офлайн-восстановления;
- `terrain_cache` — единственная запись с id 1.
- `waypoints` — локальные точки возврата;
- `altitude_alerts` — включаемые высотные пороги;
- `track_alert_events` — уже показанные направления пересечений порогов в конкретной записи.

`track_points.sessionId` ссылается на сессию с `ON DELETE CASCADE`. Индексы покрывают `sessionId` и пару `sessionId + timestampMillis`. Схема экспортируется в `app/schemas/com.apophuy.altimeter.data.local.AltimeterDatabase/`.

### Экспорт

`export/TrackExporter.kt` создаёт временные файлы в `cacheDir/exports` и отдаёт их через `FileProvider` с read URI permission.

GNSS-диагностика также создаёт только отправляемый snapshot в `cacheDir/exports`; рабочие rotating-файлы остаются в закрытом `filesDir/diagnostics`.

- GPX 1.1 включает только точки, у которых есть и latitude, и longitude; высота записывается в `<ele>`, время — UTC ISO-8601.
- CSV включает все точки и содержит timestamp, координаты, MSL-высоту, давление, горизонтальную/вертикальную точность и источник высоты.
- Числа экспортируются с `Locale.US`, чтобы десятичным разделителем всегда была точка.

Путь FileProvider ограничен `cache/exports/` в `res/xml/file_paths.xml`. Не расширяйте его без необходимости.

### UI

UI полностью реализован на Jetpack Compose. `ui/AppScreen.kt` содержит пять вкладок без Navigation Component:

- «Прибор» (`DashboardScreen.kt`): место и координаты, компас, высота и GNSS на одном экране без прокрутки;
- «История»: закреплённое снизу управление записью с отступом 16 dp от нижнего меню, список сессий и детали выбранной сессии с графиком, статистикой, экспортом и удалением;
- «Погода» (`WeatherScreen.kt`): текущие условия, давление, горизонтальная лента 24 часов и прогноз на 7 дней;
- «Точки»: сохранение текущей позиции, выбор цели, переименование, удаление и явная отправка координат;
- «Настройки»: выбор системной / светлой / тёмной темы, сведения о датчиках, независимые единицы, язык, параметры записи, ручная калибровка, opt-in GNSS-диагностика и сведения о приложении.

Dashboard подбирает диаметр компаса по доступной высоте и имеет отдельную компоновку для горизонтального экрана. `HardwareNotice.kt` показывает первое предупреждение после загрузки настроек; его подтверждение сохраняется в DataStore. Наличие rotation vector или пары акселерометр + магнитометр считается рабочим источником компаса; отсутствие одного из альтернативных источников не вызывает ложного предупреждения. `AltitudeChart.kt` рисует профиль высоты, `CompassDial.kt` — шкалу компаса, `WeatherIcon.kt` — погодные пиктограммы, `Formatters.kt` — все пользовательские преобразования и форматирование. Светлая и тёмная палитры находятся в `ui/theme/Theme.kt`. `AltimeterTheme` получает сохранённый `ThemeMode`; системный режим использует `isSystemInDarkTheme()`. Цвета приборов берутся из текущей Material-палитры, а Canvas получает их при композиции. Системные панели переключают цвет значков вместе с темой. Дневной / ночной вид погоды зависит отдельно от `is_day` в ответе API.

Любой новый пользовательский текст должен быть ресурсом, а не строковым литералом, и иметь английскую и русскую версии. Форматирование чисел в UI должно учитывать locale пользователя; экспорт, наоборот, должен оставаться locale-neutral.

## Разрешения и приватность

Manifest объявляет:

- `INTERNET` — Open-Meteo;
- `ACCESS_COARSE_LOCATION` и `ACCESS_FINE_LOCATION` — координаты, GNSS/высота и true north;
- `FOREGROUND_SERVICE` и `FOREGROUND_SERVICE_LOCATION` — запись в фоне;
- `POST_NOTIFICATIONS` — уведомление сервиса на Android 13+;
- `WAKE_LOCK` — продолжение записи при выключенном экране.

GPS, компас и барометр объявлены как необязательные hardware feature, поэтому приложение должно корректно деградировать при их отсутствии. Не добавляйте background location: текущая модель специально требует начать запись в открытом приложении, после чего работу в фоне обеспечивает foreground service.

Android backup, cloud backup и device transfer отключены для всех доменов. Не добавляйте аналитику, трекеры, облачную синхронизацию или передачу локальных треков без отдельного явного решения пользователя и обновления privacy-описания.

Диагностический лог не отправляется автоматически. Пользователь сам включает запись и вызывает системное меню «Поделиться»; установленные Telegram и другие приложения появляются в нём как обычные получатели. Не добавляйте прямую или скрытую отправку лога.

## Тесты

Локальные тесты покрывают:

- математические преобразования, фильтр высоты и порог записи точки;
- расчёт набора/сброса и extrema трека;
- состояния GNSS и vendor edge cases;
- распознавание VIVO X100 Ultra, standard/VIVO runtime policy, NMEA fix evidence, дедупликацию/сглаживание спутников и ротацию диагностического лога;
- форматирование единиц, координат и длительности;
- GPX/CSV и escaping;
- парсинг погоды, рельефа и weather code.

Инструментальные тесты в `AppLaunchTest.kt` проверяют, что dashboard открывается без принудительного системного permission dialog, и что foreground service можно запустить и остановить из «Истории». Дополнительные instrumentation-тесты проверяют компоновку разных размеров, первое предупреждение, миграцию погодного кэша с сохранением треков, ручной выбор темы и системный режим.

При исправлении дефекта сначала добавляйте тест, воспроизводящий его на самом низком подходящем уровне. Для чистой математики, resolver-ов, parser-ов и formatter-ов предпочтителен быстрый JVM unit-тест. Android-интеграционные тесты нужны для разрешений, Activity, service, Room/контекста и реального Compose-взаимодействия.

## Инварианты и зоны повышенного риска

- В публичной модели высота — над средним уровнем моря, не просто WGS84 altitude.
- Все хранимые базовые единицы метрические; пользовательские единицы относятся к отображению и вводу.
- Ручная поправка хранится в метрах и должна применяться ровно один раз.
- Activity и service совместно владеют `LiveRepository`; изменение lifecycle/reference counting легко ломает фоновую запись.
- Foreground service обязан войти в foreground своевременно и иметь тип `location`.
- На Android 13+ отсутствие permission на уведомления не должно приводить к падению при обновлении notification.
- Активная сессия должна восстанавливаться после перезапуска service/process, а не дублироваться.
- Запись зависит от настраиваемого шага высоты (по умолчанию 5 м), а не от каждого sample.
- Старые координаты нельзя приписывать новой точке трека.
- Кэш при сетевой ошибке остаётся видимым, но маркируется устаревшим.
- Отсутствие необязательного датчика не должно приводить к crash.
- Изменение Room entities без миграции приведёт к невозможности открыть существующую базу.
- Удаление сессии каскадно удаляет её точки и необратимо для пользователя.
- Экспортированные URI должны оставаться ограниченными кэшем и выдаваться только с временным read permission.

## Рекомендации по поиску причины проблемы

Начинайте с пользовательского симптома и прослеживайте данные назад до владельца состояния:

- неверная высота: UI formatter → `AltitudeReading` → калибровка → фильтр/anchor → GNSS MSL conversion и pressure input;
- неверный GNSS-статус: `GnssCard` → `LiveReading.gnss` → `GnssStateResolver` → callbacks LocationManager/GnssStatus;
- компас: `CompassDial` → declination/display rotation → rotation vector или accel+mag fallback;
- погода/рельеф: UI stale marker → repository refresh rules → HTTP/parser → Room cache;
- пропущенные точки/статистика: service sampling → `shouldStorePoint` → `TrackRepository` mutex/progress → DAO;
- потеря записи в фоне: Activity/service ownership → service lifecycle → notification permission → wake lock → active Room session;
- неверные единицы: `UserSettings` → `Formatters.kt`/notification → DataStore migration/defaults;
- проблемы экспорта: завершённость сессии → Room points → formatter → cache file → FileProvider.

Не маскируйте симптом в UI, если источник неверного состояния находится в repository, resolver, engine или хранилище.

## Взаимодействие с пользователем

- При решении описанной пользователем проблемы необходимо сначала найти суть проблемы и её главную причину
- Нужно проанализировать, какая логика и какой функционал ПО затрагивается найденной причиной
- Следует объяснить пользователю суть и причину проблемы
- Следует описать пользователю путь (возможные пути) решения
- И только после подтверждения или корректировки выбранного пути пользователем следует менять код
- Изменения в коде должны быть минимальными по объёму в рамках выбранного пути решения

Это обязательный порядок именно для исправления описанной пользователем проблемы: диагностика и согласование решения отделены от реализации. До подтверждения допустимы чтение кода, запуск проверок, воспроизведение дефекта и подготовка анализа, но не изменение рабочего кода. Если пользователь прямо просит выполнить заранее точно определённое изменение, не требующее выбора способа исправления, действуйте в рамках этого явного запроса.

## Правила внесения изменений

- Сначала определите минимальный затронутый слой и проверьте соседние потоки данных.
- Не выполняйте попутный рефакторинг, переименование или обновление зависимостей без необходимости для согласованного решения.
- Сохраняйте текущую простую архитектуру; новый framework допустим только при доказанной потребности.
- Не блокируйте main thread сетью, Room или тяжёлыми вычислениями.
- Соблюдайте structured concurrency и корректно завершайте listener, job, wake lock и service resources.
- Не проглатывайте ошибку там, где из-за этого пользователю будет показано заведомо неверное свежее значение; для сетевого кэша используйте существующую семантику `stale`.
- Не меняйте внешние пороги, формулы, cache policy и privacy-поведение как «чистку» — это продуктовые решения.
- При изменении форматов экспорта учитывайте обратную совместимость потребителей GPX/CSV.
- Не редактируйте сгенерированные build outputs. Room schema — исключение: она должна генерироваться Room после осознанного изменения БД.
- Не храните секреты и API-ключи в репозитории. Текущие API не требуют ключа.
- После реализации сообщите, какие файлы изменены, что именно проверено и какие проверки невозможно было выполнить.

## Внешние источники данных

- Open-Meteo Forecast API — текущая погода;
- Open-Meteo Elevation API — доступ к Copernicus DEM GLO-90;
- Android `AltitudeConverterCompat` — локальное преобразование эллипсоидальной GNSS-высоты к MSL;
- системный Android `Geocoder` — человекочитаемое название места.

Сеть не требуется для компаса, GNSS-координат, основной высоты, давления с датчика и записи трека. Без сети погода и рельеф доступны только из последнего кэша, а название места зависит от поведения системного геокодера.
